# Eidolon Assistant 项目交接提示词

> 把整份文件复制给另一个 AI 会话。它应当只依赖这份文件，不需要阅读之前的聊天记录。

---

## 0. 你的任务

在 macOS 上从零实现一个独立的桌面语音助手项目，目录：

```text
<repo>/
```

项目名暂定 **Eidolon Assistant**。

它是一个“角色 + DeepSeek Harness”的语音助手：

- 角色有自己的声音、人设和唤醒词；
- 用户可以用文字或语音下命令；
- 角色层判断这是闲聊还是任务；
- 任务交给内置的 DeepSeek Harness 执行；
- Harness 有控制电脑、运行 shell、读写文件、浏览网页、搜索、调用工具的能力；
- 角色把 Harness 的结果精简、角色化后用语音回复；
- 用户可以看到 Harness 的原始命令和原始输出；
- 用户可以直接绕过角色，对 Harness 下命令；
- 有确认和中断机制。

**开始实现之前，先完成第 9 节的 P0 技术验证。**
不要一上来写完整 UI，也不要假设 DSH ACP 一定能启动。

## 1. 不可违背的边界

1. **新项目必须独立。**
   - 不修改 `<prior eidolon-src>/`；
   - 不修改 `<prior eidolon-study>/`；
   - 可以把这两个项目里的角色 sheet、TTS/STT 调用方式、回复格式**复制或改写到新项目**，但不要直接依赖它们运行。

2. **只做 macOS。**
   - 不设计 Windows/Linux 安装包；
   - 不考虑服务器部署；
   - 不做移动端。

3. **不做好感度。**
   - 不引入 affinity、关系等级、礼物、冷却；
   - 不引入长期记忆；
   - 不主动搭话；
   - 不把前两个项目的好感度/记忆模块搬进来。

4. **不做“角色直接执行系统命令”。**
   - 角色层只负责判断、改写、转述、总结；
   - 真正的系统操作全部由 Harness 执行；
   - 角色层通过 HarnessBridge 发任务。

5. **不修改 DeepSeek Harness 的安装包。**
   - 不往 `/Applications/DeepSeek Harness.app` 里写文件；
   - 通过独立子进程、npm 包或 ACP 协议使用它；
   - 需要启动参数时，写在第三方项目自己的配置里。

6. **不泄露密钥。**
   - API key 只放在本地配置或环境变量；
   - 日志、UI、Harness prompt 中都不得出现完整密钥；
   - 原始日志面板要脱敏。

7. **先验证，再实现。**
   - P0 不通过时停下来报告；
   - 不要静默降级成“假 Harness”或“只做聊天”。

## 2. 用户已确认的产品决策

- 目标平台：**macOS**
- 权限策略：**默认确认高风险操作，可显式开启全部自动批准**

- 必须有取消/中断按钮，最好还有全局快捷键
- 项目不部署到服务器

## 3. 已确认的 DeepSeek Harness 接入事实

本机 DeepSeek Harness 应用版本约为：

```text
0.2.1-rc.2
```

安装位置：

```text
/Applications/DeepSeek Harness.app
```

其打包内容里已确认包含：

```text
@deepseek-ai/dsh
@deepseek-ai/dsh-acp
@deepseek-ai/dsh-acp-app
@agentclientprotocol/sdk
```

`dsh-acp` 是一个 **automation-only ACP（Agent Client Protocol）stdio JSON-RPC 服务**，支持：

```text
initialize
authenticate
session/new
session/list
session/resume
session/set_config_option
session/prompt
session/update
session/cancel
session/request_permission
session/close
```

官方说明给出的启动方式：

```text
dsh --profile acp
```

ACP 服务通过 **stdin/stdout 的新行分隔 JSON-RPC** 通信，stdout 只允许协议帧。

### 重要结论

第三项目应实现一个 **ACP 客户端**，而不是解析终端文本。

推荐流程：

```text
启动 dsh --profile acp 子进程
  → initialize
  → session/new（传入绝对工作目录）
  → session/prompt
  → 消费 session/update
  → 处理 session/request_permission
  → 需要时 session/cancel
  → session/close
```

### 启动相关的已知风险

- 本机 PATH 里没有可直接执行的 `dsh` 命令；
- ACP 服务在应用包内有运行时，但如何以独立进程启动、如何复用模型凭据，需要 P0 验证；
- 可能需要从 npm 安装 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-acp-app`，或从应用包中定位可执行入口；
- 不要修改应用包本身；
- 如果 ACP 启动失败，先报告具体错误，不要自行改成“解析普通 DSH CLI”或“自建工具循环”并继续。

## 4. 推荐技术栈

### 4.1 桌面外壳

**Electron + React + Vite + TypeScript**

原因：

- macOS 悬浮窗、置顶窗口、托盘、全局快捷键成熟；
- React 便于做快速迭代的调试面板；
- 不需要把 Next.js 服务器塞进桌面应用；
- TypeScript 与 Electron 主进程通信简单。

UI 需要：

- 无边框/浮层窗口；
- 始终置顶可选；
- 托盘图标；
- 全局快捷键；
- 状态显示：
  - 正在听
  - 正在识别
  - 正在执行任务
  - 等待确认
  - 已取消
  - 出错
- 文字输入框；
- 语音按钮 / 按住说话；
- 大号「中断」按钮；
- 原始 Harness 面板；
- 直接命令输入框；
- 关闭/隐藏/退出。

### 4.2 后端

**Python 3.12+ + FastAPI + WebSocket**

建议用本地 Python 进程负责：

- 麦克风采集；
- 本地唤醒词；
- VAD / 录音；
- STT；
- TTS；
- 角色 LLM 调用；
- 意图判断；
- 命令标准化；
- 结果总结；
- HarnessBridge（ACP 客户端）；
- SQLite 任务记录；
- 本地配置。

不要使用 WebRTC 作为这个项目的音频主链路。  
这是本机桌面助手，直接用本地音频输入/输出更简单。

可以复制/改写前两个项目中的：

- Fish Audio TTS 调用；
- Bailian/Soniox STT 调用；
- `<ja>…</ja><zh>…</zh>` 回复解析；
- 角色 sheet 结构。

### 4.3 进程关系

```text
Electron UI
   │ WebSocket
   ▼
Python FastAPI backend
   ├─ 本地音频：KWS / 录音 / 播放
   ├─ 角色 LLM / 判断模型 / 总结模型
   └─ HarnessBridge
          │ stdio JSON-RPC
          ▼
      dsh --profile acp
```

Harness 是独立子进程，不是 Python 里 import 的库。

## 5. 唤醒词设计

### 5.1 目标

不需要云端 STT 就能检测唤醒词：

```text
常驻麦克风
  → 本地 KWS
  → 检测到“拉姆”
  → 播放“我在。”
  → 启动 STT 识别后续命令
```

### 5.2 推荐评估顺序

1. **Porcupine**
   - 自定义唤醒词容易；
   - 需要确认中文/日文关键词和授权方式。
2. **sherpa-onnx KWS**
   - 开源、本地；
   - 中文关键词支持较好；
   - 适合长期方案。
3. **openWakeWord**
   - 开源可训练；
   - 中文自定义词需要额外工作。

P0 至少测一个方案，记录：

- 唤醒延迟；
- 误唤醒率；
- CPU 占用；
- 中文/日文名字的准确率；
- 播放 TTS 时是否会被自己的声音唤醒。

### 5.3 角色配置

```toml
[character]
id = "ramlethal"
name = "拉姆蕾萨尔"
wake_words = ["拉姆", "拉姆蕾萨尔"]
wake_reply = "我在。"
```

要求：

- 每个角色可以有自己的唤醒词；
- 可以支持多个唤醒词；
- 唤醒回复可自定义；
- 识别到唤醒词后，只播放固定回复，不要把唤醒词本身当作任务；
- 收到命令并完成/取消后，回到唤醒监听。

### 5.4 唤醒词失败时的兜底

必须提供：

- 全局快捷键；
- 悬浮窗上的“开始听”按钮；
- 按住说话。

如果自定义中文唤醒词效果不好，不要阻塞整个项目。

### 5.5 回声问题

播放 TTS 时必须避免自己的声音触发唤醒：

- TTS 播放期间暂停 KWS；
- 播放结束后留 300–500ms 冷却；
- 如果系统支持，启用回声消除；
- 先以“暂停 KWS”作为可靠兜底。

## 6. 角色层设计

### 6.1 角色定位

角色是“协助用户操作电脑”的助手，不是普通聊天对象。

角色 sheet 需要明确：

```text
你知道自己正在协助用户操作电脑。
你可以听到用户的命令，也可以看到 Harness 的结果。
系统操作由 Harness 执行，你负责转达、确认和总结。
```

不要写：

- “你正在和用户通话”；
- “你正在陪用户自习”；
- 好感度、礼物、主动搭话；
- 长期记忆承诺。

### 6.2 意图判断

每次收到用户输入，先调用判断模型：

```json
{
  "intent": "chat" | "task" | "ambiguous",
  "reason": "一句话理由",
  "task_hint": "如果是任务，提取任务主体"
}
```

规则：

- `chat` → 角色直接回复；
- `task` → 进入命令标准化；
- `ambiguous` → 角色先问一句澄清，不执行；
- 判断失败 → 默认按 `ambiguous` 处理，不执行系统操作。

不要用关键词硬判断作为唯一依据；关键词只能做兜底。

### 6.3 命令标准化

将用户带角色称呼、昵称、闲聊包装的命令改写成 Harness 可执行的任务描述。

输入示例：

```text
拉姆，帮我看看明天北京天气，顺便放点适合写代码的歌。
```

输出示例：

```json
{
  "task": "查询明天北京天气，并播放适合编程的背景音乐。",
  "constraints": ["使用中文结果", "音乐音量适中"],
  "requires_confirmation": false,
  "notes": "用户提到拉姆，是角色称呼，不需要传给 Harness"
}
```

要求：

- 保留任务目标、对象、约束；
- 去掉昵称、角色称呼、无意义的口癖；
- 不要擅自扩大任务范围；
- 不确定时设置 `requires_confirmation=true`；
- 原始用户输入保留在数据库和 UI 中，供审计。

### 6.4 闲聊回复

闲聊走角色人设，使用现有回复格式：

```text
<ja>日语原文</ja><zh>中文字幕</zh>
```

然后 TTS。

闲聊不启动 Harness，不产生任务日志。

### 6.5 结果总结

Harness 原始输出通常很长，必须先总结：

```text
Harness 原始输出
  → 总结模型（保留结果、风险、下一步）
  → 角色化压缩（日语 + 中文字幕）
  → TTS
```

要求：

- 不逐字复述工具日志；
- 不泄露密钥、路径中的敏感信息；
- 不把失败说成成功；
- 有错误时明确说哪一步失败；
- 需要用户确认时，用自然的角色口吻转达；
- 不冒充系统，不说“检测到系统指令”这类机械话。

## 7. HarnessBridge 设计

### 7.1 启动

HarnessBridge 负责：

- 启动 `dsh --profile acp` 子进程；
- 保持 stdin/stdout；
- 解析 JSON-RPC；
- 处理请求 ID、通知、错误；
- 管理 session；
- 记录原始事件；
- 退出时关闭 session 并终止进程。

工作目录必须使用绝对路径，建议：

```text
~/Library/Application Support/EidolonAssistant/workspace/
```

每次任务可以在同一个 session 中继续，也可以新建 session；v1 建议：

- 应用启动时创建一个持久 session；
- 每个任务作为该 session 的 prompt；
- 任务之间保留上下文；
- 用户可以手动“新任务/清空上下文”。

### 7.2 必要方法

至少实现：

```text
initialize
session/new
session/prompt
session/update（通知）
session/request_permission（服务端请求）
session/cancel
session/close
```

### 7.3 确认

Harness 发 `session/request_permission` 时：

1. 提取权限请求的动作、风险、可选选项；
2. 交给角色层生成自然语言；
3. UI 同时显示原始权限请求；
4. 用户说“可以/继续/允许”或点允许；
5. Bridge 返回对应 allow 选项；
6. 用户拒绝 → 返回 reject；
7. 超时/无回答 → 不执行，保持等待或取消。

角色示例：

```text
「它想把工作区里的两个文件删掉。要继续吗？」
```

不要机械复述 ACP 的 JSON。

### 7.4 取消

取消入口：

- 悬浮窗大按钮；
- 全局快捷键；
- 语音“停 / 取消 / 中断”；
- 关闭窗口/退出应用时也要清理。

取消流程：

1. 停止 TTS；
2. 停止当前 STT；
3. 调用 `session/cancel`；
4. 等待 ACP 取消；
5. 超时则 kill Harness 子进程组；
6. 清理本次任务的临时状态；
7. 回到唤醒监听。

必须有后端兜底，不能只依赖 UI。

### 7.5 原始访问

UI 提供两个入口：

1. **任务详情**
   - 原始用户输入；
   - 标准化命令；
   - ACP 事件；
   - 工具调用；
   - Harness 原始输出；
   - 错误。

2. **直接命令**
   - 绕过角色层；
   - 直接把用户输入发给 Harness；
   - 仍经过权限和取消机制；
   - 仍然记录日志。

直接命令是高级功能，必须在 UI 中明确标识。

## 8. 权限策略

用户选择“按建议来”，即：

### 默认自动允许

- 读取文件；
- 列目录；
- 搜索网页；
- 读取网页；
- 查询信息；
- 播放音乐/打开应用（非破坏性）；
- 只读系统信息。

### 默认需要确认

- 写文件；
- 删除/移动/覆盖文件；
- 执行任意 shell；
- 修改系统设置；
- 安装/卸载软件；
- 上传文件或数据；
- 访问密钥/凭据；
- 支付、购买、发送消息；
- 任何不可逆操作；
- 任何 Harness 主动请求确认的操作。

### 必须有的保护

- 专用工作目录；
- 不把用户主目录整个交给 Harness；
- 日志脱敏；
- 全局中断；
- “全部自动批准”必须显式开启，并在 UI 持续显示警告；
- 退出应用时终止所有 Harness 子进程。

“完全权限”可以配置，但不能没有边界和审计。

## 11. 验收标准

必须逐项演示：

1. 说“拉姆”，本地唤醒，播放“我在。”，不调用云端 STT 做唤醒。
2. 说“拉姆，帮我查一下明天北京天气”，角色判断为任务，Harness 执行，角色用简短日语 + 中文字幕总结。
3. 说“拉姆，我今天有点累”，判断为闲聊，不启动 Harness。
4. 执行需要权限的任务时，角色自然询问；用户拒绝，Harness 不执行。
5. 执行长任务时按中断，1 秒内停止 TTS 和任务，不留下 Harness 子进程。
6. 打开任务详情，能看到原始用户输入、标准化命令、工具调用、原始输出。
7. 直接命令输入可以绕过角色，但仍然经过权限和取消。
8. 播放 TTS 不会触发自己的唤醒词。
9. 没有好感度、没有长期记忆、没有主动搭话。
10. 退出应用后没有本地 Harness 子进程残留。

## 12. 已知风险与停止条件

### 风险

- ACP 独立启动/认证/打包不成功；
- 自定义中文/日文唤醒词准确率不足；
- Electron + Python 打包复杂；
- DSH 的权限请求语义和预期不同；
- TTS 回声导致自唤醒；
- Harness 全权限带来安全风险；
- 长任务、后台进程、工具超时处理复杂；
- macOS 辅助功能/麦克风权限。

### 停止条件

出现以下情况，先停下报告，不要假装完成：

- ACP 完全无法启动；
- 无法获得任何 Harness 工具事件；
- 取消无法终止任务；
- 权限请求无法响应；
- 唤醒词方案完全不可用且兜底也未实现。
